# 여러 기기에서 학습 진행 이어 가기: 현재 상태와 설계안

작성 2026-11-17. 이 문서는 설계안이다. **2026-11-18 갱신: 5절의 1단계(동기화 폴더 내보내기·기록 단위 합치기)를 구현했다.** 8절 참고.

## 1. 문제를 한 문장으로

비유하면 지금 Duvi의 학습 기록은 **집마다 따로 둔 공책**이다. 집 PC에서 쓴 질문은 사무실 PC 공책에 없다.
옮기려면 공책을 복사해서 들고 가야 하고(백업 JSON), 양쪽에서 같은 쪽을 고쳤다면 어느 쪽을 남길지 정해야 한다(충돌).

## 2. 지금 무엇이 어디에 저장되나 (소스 기준)

| 위치 | 내용 | 기기 사이에 옮겨야 하나 |
|---|---|---|
| `backend/learning/state.json` | 질문·설명 기록, 수정·복습 이력, 자료별 학습 상태와 완료 표시, 전역 `revision` | **예, 핵심** |
| `backend/learning/before-import.json`, `import-journal.json` | 복원 직전 사본, 복원 중단 복구 기록 | 아니요(기기별) |
| `backend/library/*.json`, `folders.json` | YouTube 강의 메타데이터·영어 자막, 폴더와 순서 | 선택(로드맵 "강의 폴더 준비"와 자막 자동 준비로 다시 만들 수 있음) |
| `backend/data/` | MIT 영어 자막 | 아니요(`npm run setup`으로 다시 받음) |
| `backend/translations/` | ChatGPT 한국어 번역 캐시 | 선택(용량이 크고, 다시 번역하면 비용이 듦) |
| 브라우저 localStorage | 재생 위치, 자막 크기·위치, 저장 전 초안(`duvi-learning-drafts-v1`), 기기 내 번역 | 재생 위치·설정만 선택. 초안은 제외 |
| `%LOCALAPPDATA%/StudyLibraryPreview/accounts.dpapi` | ChatGPT 인증 정보(Windows DPAPI 암호화) | **절대 아니요.** DPAPI는 그 Windows 사용자에게 묶여 있어 다른 PC에서 풀 수도 없다 |

현재 옮기는 방법은 앱의 **백업·복원** 하나다.

- 내보내기 `GET /api/learning/export`: 학습 상태·강의·폴더·번역을 `schemaVersion: 1` JSON으로 만든다. 화면은 허용된 브라우저 키(재생 위치·자막 설정)를 덧붙인다. 최대 16MB. 인증 정보와 초안은 빠진다.
- 가져오기: 먼저 미리보기(`/api/learning/import/preview`)로 항목 수와 같은 ID 충돌을 보여 주고 10분짜리 토큰을 준다. 확정(`/api/learning/import`) 때 정책을 고른다.
  - `merge`(현재 기록 유지): 같은 ID가 있으면 **이 PC의 것을 남기고** 없는 항목만 더한다.
  - `replace`(백업으로 덮어쓰기): 같은 ID면 **백업의 것으로 바꾸고**, 이 PC에만 있는 항목은 남긴다. 덮어쓴 기록의 `revision`은 둘 중 큰 값 + 1이 된다.
  - 확정 전 현재 상태를 `before-import.json`에 저장하고, 쓰기 도중 실패하면 journal로 되돌린다.

알아 둘 한계:

1. **충돌 단위가 "기록 한 장 전체"다.** 두 PC에서 같은 기록을 고쳤다면 한쪽 수정은 통째로 버려진다. 버려진 쪽은 그 PC의 `before-import.json`에만 남는다.
2. **`revision`은 한 서버 안의 순서표다.** 비유하면 두 집 공책의 쪽 번호와 같아서, 두 PC가 각자 매긴 번호를 비교해도 어느 쪽이 나중인지 알 수 없다. 공통 기준점(마지막으로 맞춘 시점)을 기억하지 않는다.
3. **학습 상태는 시각을 보지 않는다.** 정책에 따라 한쪽 값이 이긴다. 한 PC에서 완료를 취소하고 다른 PC에서 완료했다면 정책에 따라 결과가 갈린다.
4. **휴대폰은 지금 구조로 접속할 수 없다.** 서버는 `127.0.0.1`에만 열리고 Host 헤더도 확인한다. 실행에는 Windows가 필요하다(DPAPI, `yt-dlp.exe`). 여기서 "여러 기기"는 여러 Windows PC를 뜻한다.

## 3. 공통 원칙

- **개인 데이터는 공개 Duvi 저장소에 두지 않는다.** `.gitignore`가 이미 `backend/learning/`, `backend/library/`, `backend/translations/`를 제외한다. 동기화 파일은 저장소 밖 폴더에 둔다.
- **인증 정보는 옮기지 않는다.** 각 PC에서 다시 로그인한다.
- **오프라인에서도 공부할 수 있어야 한다.** 동기화는 공부를 막지 않는 별도 단계다.
- **기록은 지우지 않고 쌓는다.** 이미 최초 설명·수정 이력·복습 이력을 보관하므로, 충돌한 쪽도 이력으로 남길 수 있다.

## 4. 설계안 세 가지

### A. 클라우드 폴더(OneDrive·Google Drive·Dropbox)로 내보내기 파일 주고받기

비유: 공책 사진을 공유 사진첩에 올리고, 다른 집에서 받아 내 공책에 옮겨 적는다.

- 각 PC가 `<클라우드>/Duvi-sync/<기기ID>.json`에 **자기 학습 상태만** 내보낸다(기록·상태, 수십 KB 수준). 강의·번역은 넣지 않거나 따로 둔다.
- 앱을 열 때 다른 기기 파일을 읽어 미리보기를 보여 주고, 4.4절 규칙으로 합친다.
- **`backend/` 폴더 자체를 클라우드로 동기화하지는 않는다.** 서버는 임시 파일을 쓴 뒤 이름을 바꾸는 방식으로 저장하는데, 두 PC가 동시에 쓰면 클라우드 프로그램이 "state-PC2.json" 같은 사본을 만들거나 한쪽을 덮어쓴다. 복원 journal이 다른 PC의 파일을 되돌릴 수도 있다.
- 장점: 서버가 필요 없다. 오프라인 작업 뒤 파일만 맞추면 된다. 사용자가 이미 쓰는 클라우드를 쓴다.
- 단점: 클라우드 회사가 파일을 읽을 수 있다. 원하면 비밀번호로 암호화(브라우저 WebCrypto AES-GCM)한 뒤 올린다.

### B. 비공개 Git 저장소에 내보내기 파일 커밋

비유: 공책 사본을 날짜별로 금고에 넣어 두고, 꺼낼 때 비교한다.

- 별도 **비공개** 저장소(예: `duvi-learning-private`)에 기기별 JSON을 커밋한다. 이력 전체가 남아 "언제 무엇을 바꿨나"를 추적하기 좋다.
- 단점: Git 설치와 인증이 필요하다. 실수로 공개 저장소에 올릴 위험이 있다. 번역까지 넣으면 저장소가 금방 커진다(백업 최대 16MB).
- Duvi 규칙상 "학습 행동으로 외부 저장소에 자동 push"는 하지 않는다. 사용자가 직접 커밋·push한다.

### C. 작은 자체 호스팅 동기화 API

비유: 공책을 한 권만 두고 모든 집이 그 공책에 쓴다.

- 집 PC나 작은 서버에 동기화 API를 두고, 각 Duvi가 "내 마지막 동기화 이후 바뀐 기록"을 올리고 받는다.
- 장점: 거의 실시간이다. 나중에 휴대폰 화면을 만들 길도 열린다.
- 단점: 인증·TLS·백업·서버 운영이 필요하다. 지금 앱은 로컬 전용 보안 모델(127.0.0.1, CSRF, 같은 출처)이라 바꿀 것이 많다. 지금 단계에는 과하다.

### 4.4 세 안에 공통인 합치기 규칙

지금의 "한 장 전체 유지/덮어쓰기" 대신 다음 규칙을 쓴다. 기록 형식은 거의 그대로 두고, 기기별 마지막 동기화 기준만 로컬 파일(`backend/learning/sync-state.json`, Git 제외)에 따로 둔다.
유일한 형식 변경 후보는 `history` 항목에 "어느 기기의 수정본인가"를 적는 필드 하나다(지금 항목은 `revision`·`at`·`record`만 허용).

| 데이터 | 규칙 | 이유 |
|---|---|---|
| 서로 다른 ID의 기록 | 모두 합친다 | 기록 ID가 UUID라 기기 사이에 겹치지 않는다 |
| 복습 이력 `reviews` | ID 기준 합집합 | 복습은 추가만 되는 기록이다 |
| 같은 기록을 한쪽만 고침 | 고친 쪽을 쓴다 | 마지막 동기화 때의 `revision`과 비교해 판단한다 |
| 같은 기록을 양쪽에서 고침 | `updatedAt`이 늦은 쪽을 현재 값으로 두고, 다른 쪽 내용을 `history`에 "다른 기기 수정본"으로 덧붙인 뒤 확인 표시 | 아무 설명도 버리지 않는다 |
| 학습 상태·완료 표시 | 자료 ID마다 `updatedAt`이 늦은 쪽 | 완료 취소도 기록으로 남는다 |
| 브라우저 재생 위치 | 강의마다 더 뒤의 위치(선택) | 이어 보기 |
| 초안, 인증 정보 | 동기화하지 않음 | 개인 입력 중인 내용과 비밀 |

## 5. 추천

**지금 당장(코드 없이): "바통 넘기기" 방식.** 한 번에 한 PC에서만 공부한다는 규칙을 둔다.

1. PC를 바꾸기 전에 **학습 로드맵 → 백업·복원 → 전체 백업 내려받기**로 받은 파일을 개인 클라우드 폴더에 저장한다(공개 Git 금지).
2. 다른 PC에서 그 파일을 선택하고, 미리보기를 확인한 뒤 **"백업 기록으로 충돌 항목 덮어쓰기"**로 복원한다.
   방금 공부한 PC의 기록이 이기고, 이 PC에만 있는 기록은 남는다. 덮어쓴 이전 상태는 `before-import.json`에 남는다.
3. 두 PC에서 같은 기록을 따로 고쳤다면 한쪽 수정은 현재 값에서 사라진다. 이 경우는 위 규칙으로 피한다.

**다음 구현(작은 코드 변경 두 개):** 안 A를 두 단계로 만든다.

1. 학습 상태만 담은 가벼운 내보내기(기록·상태, 강의·번역 제외)와 "동기화 폴더" 설정. 지금의 미리보기·명시 확정 흐름을 그대로 쓴다.
2. 4.4절 합치기 규칙을 `merge`·`replace` 옆의 세 번째 정책으로 추가하고 테스트한다(기존 `backend/tests/learning-backup.test.mjs` 옆).

B는 이력 추적이 꼭 필요할 때만, C는 휴대폰 화면을 만들기로 결정할 때 다시 검토한다.

## 6. 2026-11-17에 구현하지 않았던 이유

- 안전한 동기화의 핵심은 4.4절 합치기 규칙인데, 이것은 백업·복원의 충돌 정책을 바꾸는 일이다. 이 저장소 규칙은 "복원은 검증된 미리보기와 명시적 충돌 정책을 거친다"이다. 자동으로 합치는 기능은 그 원칙에 맞게 설계·검토한 뒤 넣어야 한다.
- 기기별 동기화 기준(`sync-state.json`)과 양쪽 수정 이력 보존은 작은 변경이 아니고, 실제 두 PC에서 확인해야 한다. 이번 작업 환경에는 PC가 하나뿐이었다.

## 7. 확인 범위

- 2절은 `backend/learning.mjs`, `backend/learning-backup.mjs`, `backend/learning-backup-schema.mjs`, `backend/learning-validation.mjs`, `backend/http-server.mjs`, `server.mjs`, `src/learning-backup-ui.mjs`를 읽고 정리했다.
- 백업 내보내기·복원은 이번에 브라우저에서 실행하지 않았다. 두 PC 사이의 실제 이동도 하지 않았다.

## 8. 구현된 1단계 (2026-11-18)

- 코드: `backend/learning-sync.mjs`(API `/api/learning/sync*`), 화면 `src/learning-sync-ui.mjs`(학습 → 백업·동기화), 테스트 `backend/tests/learning-sync.test.mjs`.
- 각 PC는 동기화 폴더에 `duvi-sync-<기기ID>.json` 하나만 쓴다. 담는 것은 학습 상태(기록·수정/복습 이력·자료별 상태)뿐이고 강의·번역·계정·초안은 담지 않는다.
- Git 작업 트리 안의 폴더와 Duvi 데이터 폴더는 동기화 폴더로 거부한다(개인 기록이 공개 저장소에 들어가지 않게).
- 가져오기는 미리보기(10분 유효) → 확인 체크 → 합치기 순서다. 합치기 직전 상태는 `before-sync.json`에 남는다.
- 합치는 규칙은 4.4절과 같다. 한쪽이 다른 쪽을 이어 고쳤으면 그쪽을 쓰고, 두 PC에서 따로 고쳤으면 나중 수정을 현재 값으로 두고 다른 쪽을 "다른 PC 수정본"으로 수정 이력에 남긴다. 복습은 합치고 자료별 상태는 `updatedAt`이 늦은 쪽이 이긴다.
- 확인: 한 PC에서 두 개의 격리된 데이터 폴더로 서버 둘을 띄워 브라우저에서 내보내기 → 가져오기 → 양쪽 수정 충돌 → 이력 보존을 실행했다. 실제 OneDrive 같은 클라우드 동기화 지연·파일 잠금과 물리적으로 다른 두 PC는 확인하지 않았다. 2단계(자동 동기화)는 구현하지 않았다.
